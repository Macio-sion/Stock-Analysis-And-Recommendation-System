本文档依据现有设计文档，将项目开发划分为 12 个阶段，每个阶段对应一个可独立交付、可验证的功能集群。

|------|----------|----------|
| 1 | 项目骨架 + 持久化基础设施 | — |
| 2 | 数据接入层（Tushare + 舆情本地库 + 缓存） | 1 |
| 3 | 阶段一 · 技术分析师 + 基本面分析师 | 2 |
| 4 | 阶段一 · 舆情分析师 + 汇总节点 | 2、3 |
| 5 | LLM 层 + ReAct 引擎 | 1（可与 3/4 并行） |
| 6 | 阶段二 · 多头/空头研究员 | 4、5 |
| 7 | 阶段二 · 研究经理 | 6 |
| 8 | 阶段三 · 策略执行（默认推荐管线） | 7 |
| 9 | 任务队列 + 并发执行（Redis 队列 + Worker） | 8 |

## 模块可测试性约定

每个开发阶段交付的功能模块都必须满足「可独立测试」要求，便于逐模块数据测试。

1. **单一职责**：每个模块只做一件事（如「指标计算」「趋势判断」），不混合多个职责。
2. **清晰接口**：每个模块暴露明确的输入/输出签名（函数/方法），不依赖隐式全局状态。
3. **数据契约**：模块间通过已定义的 State/数据结构传递，字段名与类型与设计文档一致。
4. **可独立测试**：每个模块能脱离完整工作流，用样例数据单独调用并验证输出。
5. **附带样例**：每个模块交付时附带「输入样例 + 期望输出」，供数据测试。

数据测试方式：每个模块提供独立入口（脚本或测试函数），输入样例数据即可验证；建议配套 `tests/` 下的测试函数与一组真实数据样例。

## 阶段 1：项目骨架 + 持久化基础设施

**目标**：搭好工程地基，保证后续所有阶段有可依赖的运行骨架。

**任务**
1. 初始化项目目录结构、`requirements.txt`、`pyproject.toml`、`.env.example`。
2. 实现全局配置 `config/settings.py` 与日志配置（loguru + `logging_config.py`）。
3. 实现 PostgreSQL 连接管理（`persistence/database.py`）与 7 张表的 ORM 模型（`models.py`）。
4. 实现状态存储/读取 `repository.py`，含 `scripts/init_db.py` 建表脚本。
5. 接入 Redis 缓存（`data/cache.py`）。

**交付物**：可启动的工程骨架、可落地的 7 表结构、日志与配置。

**验收标准**：工程能启动；数据库/Redis 连通；`init_db.py` 成功建表；日志按级别输出。

**可测接口**：
- `init_db()` → 建表结果
- `save_snapshot(workflow_id, agent_name, state)` → 布尔
- `get_latest_snapshot(workflow_id, agent_name)` → state 快照
- 自测：运行 init_db 建表，写入并读回一条快照，字段一致。

## 阶段 2：数据接入层

**目标**：统一封装外部数据源，为阶段一分析师提供数据。

**任务**
1. 实现 Tushare 客户端（`data/tushare_client.py`）——行情 `daily` 与财务 `fina_indicator`。
2. 实现舆情 HTTP 请求获取（`data/sentiment_client.py`，从 alphaAI 网站）。
3. 数据获取结果写入 Redis 缓存（带 TTL）。
4. 提供 `scripts/test_tushare.py` 连接自检。

**交付物**：三个数据源的可调用封装 + 缓存。

**验收标准**：能拉取指定股票行情/财务数据；能查询舆情数据；重复调用命中缓存。

**可测接口**：
- `get_daily(ts_code, start_date, end_date)` → OHLCV DataFrame
- `get_fina_indicator(ts_code, period)` → 财务指标 DataFrame
- `fetch_sentiment(symbol, start_date, end_date)` → 舆情 JSON（新闻/帖子列表）
- 自测：拉取一只股票，检查字段完整、无空值异常。

## 阶段 3：阶段一 · 技术分析师 + 基本面分析师

**目标**：完成阶段一的前两个硬编码分析师（同依赖 Tushare，模式一致）。

**任务**
1. 实现技术分析师（指标计算 → 趋势判断 → 报告），`TechnicalAgentState`。
2. 实现基本面分析师（维度评分 → 估值判断 → 报告），`FundamentalAgentState`。
3. 定义两份报告的字段结构，结果落库 `agent_state_snapshots`。

**交付物**：技术分析报告 + 基本面分析报告。

**验收标准**：给定股票代码与时间窗口，输出技术报告（趋势/关键价位/评分）与基本面报告（估值/评分/优势风险），指标计算正确。

**可测接口**：
- `calc_indicators(raw_ohlcv)` → indicators
- `judge_trend(indicators)` → trend_analysis
- `gen_technical_report(trend_analysis)` → technical_report
- `calc_dimension_scores(financial_raw)` → dimension_scores
- `judge_valuation(valuation_raw)` → valuation
- `gen_fundamental_report(...)` → fundamental_report
- 自测：输入样例 OHLCV/财务数据，验证指标数值与评分正确。

## 阶段 4：阶段一 · 舆情分析师 + 汇总节点

**目标**：补齐阶段一并完成汇聚，闭环阶段一。

**任务**
1. 实现舆情分析师（NLP → 情绪量化 → 报告），`SentimentAgentState`。
2. 实现汇总节点，输出 `StageOneMergeState`（三报告 + 三维度得分）。
3. 三分析师并行编排 + 汇聚接入 LangGraph 骨架。

**交付物**：舆情报告 + 阶段一汇聚状态。

**验收标准**：输入股票代码，三分析师并行产出报告并汇聚为 `StageOneMergeState`。

**可测接口**：
- `nlp_analyze(social_raw)` → nlp_results
- `quantify_sentiment(nlp_results)` → sentiment
- `gen_sentiment_report(sentiment)` → sentiment_report
- `merge_reports(tech, fund, sent)` → StageOneMergeState
- 自测：输入样例舆情数据，验证情绪量化与三报告汇聚。

## 阶段 5：LLM 层 + ReAct 引擎

**目标**：实现 LLM 调用与 ReAct 循环，为阶段二提供推理能力（可与阶段 3/4 并行）。

**任务**
1. 实现 LLM 客户端（`llm/client.py`，Ollama/OpenAI）。
2. 实现 ReAct 循环引擎（`llm/react_engine.py`，思考-行动-观察 + 轮次上限）。
3. 实现结构化输出解析器（`llm/output_parser.py`）。
4. 实现 ReActContext（消息管理 + 上下文压缩）。

**交付物**：可复用的 LLM 推理基座。

**验收标准**：能用 LLM 完成一轮 ReAct 循环并解析出结构化 JSON；轮次上限与退出原因生效。

**可测接口**：
- `chat(messages)` → LLM 响应
- `react_loop(state)` → 最终结构化输出 + exit_reason
- `parse_output(text)` → Pydantic 对象
- 自测：给定样例提示词，验证 LLM 返回可解析结构，轮次上限生效。

## 阶段 6：阶段二 · 多头/空头研究员

**目标**：实现多空辩论的两个对立研究员。

**任务**
1. 实现多头研究员（`BullishAgentState` + `BullishReport`），工具集（读三报告 + 搜索）。
2. 实现空头研究员（`BearishAgentState` + `BearishReport`）。
3. 接入提示词（`bull_researcher.py` / `bear_researcher.py`）。

**交付物**：多头观点报告 + 空头观点报告。

**验收标准**：输入三份报告，分别输出看涨/看跌观点报告，论据 ≥3 条且含来源/权重/引用，置信度分解完整。

**可测接口**：
- `run_bull(state)` → bull_report
- `run_bear(state)` → bear_report
- 自测：输入三份样例报告，验证多空报告的论据/置信度字段完整。

## 阶段 7：阶段二 · 研究经理

**目标**：实现多空裁决，闭环阶段二。

**任务**
1. 实现研究经理（`ResearchManagerState` + `ComprehensiveReport`），工具集（读多空报告 + 搜索）。
2. 实现共识识别 + 分歧裁决 + 综合评分与评级逻辑。
3. 接入提示词（`research_manager.py`）。

**交付物**：综合分析报告（评级/共识/分歧/综合评分）。

**验收标准**：输入多空报告，输出综合分析报告，评分可解释（三维度 + 辩论调整分），评级映射正确。

## 阶段 8：阶段三 · 策略执行（默认推荐管线）

**目标**：实现默认硬编码推荐管线，打通完整推荐链路。

**任务**
1. 实现策略匹配引擎（识别 6 类策略 + 权重加载）。
2. 实现评分计算器（加权 + 置信区间 + 历史基准）。
3. 实现推荐决策器（阈值 → 买入/持有/回避 + 理由构建），`StrategyAgentState`。
4. 三阶段 LangGraph 全链路串联，`recommendations` 落库。

**交付物**：最终推荐结果（action/score/reasoning）。

**验收标准**：输入综合分析报告 + 策略，正确按权重算分并映射到推荐动作；完整链路（输入股票 → 推荐）跑通。

## 阶段 9：任务队列 + 并发执行

**目标**：实现多用户并发访问的异步任务执行，保证接口响应性与资源可控。

**任务**
1. 实现 Redis 任务队列（`LPUSH` 入队 / `BRPOP` 阻塞消费）。
2. 实现 Worker 进程（消费队列，执行 `graph.invoke`，更新状态）。
3. 同步 API 层（校验 + 入队 + 立即返回 workflow_id）与异步 Worker 层分离。
4. 任务状态查询（Redis 实时状态 + PostgreSQL 持久化）。
5. 幂等、失败重试、任务超时、Worker 心跳。

**交付物**：Redis 任务队列 + Worker 异步执行链路。

**验收标准**：多用户并发提交任务时接口低延迟返回 workflow_id；Worker 异步消费并执行；任务状态可查询。

**可测接口**：
- `enqueue_task(task)` → 入队结果
- `run_worker()` → 消费并执行任务
- `get_task_status(workflow_id)` → 任务状态
- 自测：提交任务入队，Worker 消费执行，查询状态。

## 阶段 10：前端 Web 界面（Streamlit）

**目标**：提供可交互界面，实现「提交 → 结果展示 + 可视化」。

**任务**
1. 登录界面 + 主界面导航。
2. 智能推荐分析页（任务提交、结果/数据可视化、推荐结果展示）。

**交付物**：可用 Web 界面。

**验收标准**：用户通过界面完成一次完整推荐（输入股票 → 查看三阶段结果 → 最终推荐 + 图表）。

**可测接口**：
- 页面「提交任务 → 状态查询 → 结果展示」链路
- 自测：端到端提交一只股票，查看三阶段结果与推荐。

## 阶段 11：自定义算法在线执行

**目标**：实现核心扩展能力——用户自定义算法在线生成、执行与实时可视化。

**任务**
1. 代码生成引擎（`codegen/`：LLM 生成 Python + AST 静态校验），`CodeGenSandboxState`。
2. Docker 沙箱执行器（`sandbox/`：容器创建 → 编译 → 执行 → 资源限制）。
3. WebSocket 流式推送（`streaming/`：code/log/metric/status 事件）。
4. 前端自定义算法页（代码展示 + 执行日志 + 分析曲线图）。
5. 接入提示词（`code_generator.py`）。

**交付物**：自定义算法在线执行管线 + 实时可视化。

**验收标准**：自然语言描述 → 生成代码 → 沙箱执行 → 前端实时看到代码/日志/曲线；危险代码被拦截、超时正常终止。

**可测接口**：
- `generate_code(description)` → GeneratedCode
- `validate_code(code)` → validation
- `execute(code)` → result + logs + metrics
- 自测：输入算法描述，验证生成→校验→执行，实时日志/曲线输出。

## 阶段 12：安全加固 + 部署运维 + 测试收尾

**目标**：达到可上线质量。

**任务**
1. 安全加固（沙箱资源限制/网络禁用/最小权限、密钥环境变量注入、鉴权、日志脱敏）。
2. 部署（`docker-compose.yml` 编排、环境变量、监控告警）。
3. 测试补齐（单元/集成/端到端），覆盖 `测试与验收标准.md` 的用例。

**交付物**：可部署、安全、测试达标的系统。

**验收标准**：docker-compose 一键启动；危险代码被拦截；测试通过率达标；监控告警生效。

**可测接口**：
- 安全：危险代码拦截、超时终止
- 部署：docker-compose 启动
- 测试：单元/集成/端到端通过率
- 自测：按「测试与验收标准.md」用例逐项验证。

```
阶段1 ──→ 阶段2 ──→ 阶段3 ──→ 阶段4 ──→ 阶段6 ──→ 阶段7 ──→ 阶段8 ──→ 阶段9 ──→ 阶段10
   └──────────────→ 阶段5 ──────────────↗（阶段5 可与 3/4 并行）
                                                      ↘ 阶段11（依赖 5、8）
                                                      阶段12（依赖全部）
```

- **可并行**：阶段 5（LLM/ReAct）可与阶段 3、4 并行开发。
- **里程碑**：阶段 4 完成 = 阶段一闭环；阶段 7 完成 = 阶段二闭环；阶段 8 完成 = 主链路 MVP；阶段 9 完成 = 并发异步执行；阶段 11 完成 = 核心差异化能力。
