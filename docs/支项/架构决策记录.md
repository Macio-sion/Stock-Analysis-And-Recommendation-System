# 架构决策记录（ADR）

## ADR-001：采用 LangGraph 编排工作流
- **背景**：系统由多个 agent 组成三阶段工作流，需要支持并行分支、状态传递与断点恢复。
- **决策**：使用 LangGraph 作为工作流编排框架。
- **理由**：原生支持有向图、条件分支、状态共享与 checkpoint（断点续传），与 LangChain 生态无缝集成。
- **替代方案**：手写编排（灵活但需自行实现状态/重试）、Airflow（偏批处理，实时交互弱）。
- **后果**：引入 LangGraph 依赖，需遵循其 State/Node 范式。

## ADR-002：PostgreSQL + Redis 双层存储
- **背景**：需要持久化工作流状态/报告（结构化、可查询），同时缓存热点行情/舆情数据降低外部 API 调用。
- **决策**：PostgreSQL 持久化 + Redis 缓存。
- **理由**：PostgreSQL 支持 JSONB（存储 Agent 状态快照）与关系查询；Redis 提供高性能缓存与 TTL。
- **替代方案**：纯 Redis（持久化弱）、MongoDB（事务弱）。
- **后果**：维护两套存储，需明确事务边界（见持久化设计）。

## ADR-003：Streamlit 作为前端
- **背景**：需要快速构建 Web 交互界面，含数据展示与可视化。
- **决策**：使用 Streamlit。
- **理由**：Python 原生、开发快、内置图表组件，与后端同栈。
- **替代方案**：React/Vue + 独立前端工程（体验更好但成本高）。
- **后果**：交互能力受限，WebSocket 实时推送需额外集成。

## ADR-004：Docker 沙箱执行用户自定义代码
- **背景**：用户可在线提交并执行自定义推荐算法，存在恶意代码风险。
- **决策**：用户代码在独立 Docker 容器中隔离执行。
- **理由**：容器提供进程/网络/文件系统隔离，配合资源限制可实现强隔离；优于进程内 `eval`。
- **替代方案**：受限 AST 白名单（隔离弱）、独立子进程（隔离中等）、远端 Serverless 执行（复杂）。
- **后果**：引入 Docker 依赖与容器编排成本，每次执行有容器冷启动开销。

## ADR-005：LLM 生成自定义算法代码
- **背景**：目标 5 要求用户以自然语言/伪代码描述算法，系统在线生成可执行代码。
- **决策**：由代码生成器（ReAct + LLM）将描述转换为 Python 代码，经 AST 校验后执行。
- **理由**：LLM 擅长将自然语言转换为代码，配合结构化输出保证可解析。
- **替代方案**：可视化表单生成代码（受限）、模板拼接（灵活性差）。
- **后果**：LLM 生成代码存在不确定性与安全风险，需 AST 校验 + 沙箱双重兜底。

## ADR-006：三阶段「硬编码 + ReAct + 硬编码」编排
- **背景**：不同 agent 的特性差异大——阶段一数据计算确定性高，阶段二需要推理辩论，阶段三推荐需稳定可解释。
- **决策**：阶段一/三用硬编码确定性流程，阶段二用 ReAct 智能体。
- **理由**：硬编码保证数据计算与推荐结果的稳定可解释；ReAct 发挥 LLM 推理能力处理多空辩论。
- **替代方案**：全 ReAct（成本高、结果不稳定）、全硬编码（失去推理能力）。
- **后果**：系统同时维护硬编码节点与 ReAct 引擎两套执行范式。

## ADR-007：Redis 任务队列 + 同步异步分离
- **背景**：推荐分析是长耗时任务，多用户并发时需保证接口响应性与资源可控。
- **决策**：API 层同步入队即返回，Worker 层异步消费 Redis 任务队列执行。
- **理由**：同步部分不执行重计算，接口低延迟；异步 Worker 可横向扩展、削峰、故障重试。
- **替代方案**：同步阻塞执行（接口卡死）、纯多线程（扩展性弱）、Celery（重但功能全）。
- **后果**：引入任务队列与 Worker 进程，需处理幂等、超时、重试与监控。
