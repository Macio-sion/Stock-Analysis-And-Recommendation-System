# 技术探讨纪要

本文档汇总开发过程中在技术选型、架构设计上的探讨与决策，记录「问题 → 结论 → 取舍理由」，作为后续开发的决策基线。

## 1. 分层架构：硬编码 / ReAct / 编排

- **问题**：阶段一（数据获取与分析）为什么不用 LangChain 做业务逻辑？最后如何统一编排？
- **结论**：采用三层分离——业务逻辑层（纯 Python/pandas）、LLM 推理层（LangChain ReAct）、编排层（LangGraph）。
- **理由**：阶段一的指标计算是确定性计算，用 LangChain 是过度设计；LangChain 的价值在 LLM 调用/工具编排/ReAct 循环，只用于阶段二的推理型任务；LangGraph 只管节点调度、并行、汇聚、断点恢复，不关心节点内部实现。对应 ADR-006。

## 2. LangGraph 节点的范围

- **问题**：阶段一、阶段三只需要处理数据，还是也要作为节点构建图？
- **结论**：三阶段全部作为 LangGraph 节点；阶段一/三是「普通函数节点」，阶段二是「ReAct agent 节点」，只有阶段二节点内部用 LangChain。
- **理由**：节点是 LangGraph 的统一抽象，与「节点内部实现」正交。阶段一/三进图才能获得状态自动流转、并行执行、断点续传三大能力。

## 3. 环境与运行约束

- **问题**：依赖装在虚拟环境还是本机？模型服务用什么？
- **结论**：项目用本机 Python 环境构建运行；`.venv` 仅供沙盒工具临时使用；模型服务用本机 Ollama，不装 OpenAI SDK。
- **理由**：本机已有依赖与模型；沙盒禁止写入系统 site-packages，依赖由用户在本机手动安装。

## 4. LLM 客户端：ChatOllama vs 原生 requests

- **问题**：用 requests 直接调 Ollama，还是用 langchain-ollama 的 ChatOllama？requests 能否绑定工具和结构化输出？
- **结论**：改用 `ChatOllama`，用 `bind_tools` 绑定工具、`with_structured_output` 约束结构化输出。
- **理由**：requests 方式的「伪绑定」靠手动解析文本 `{"tool":...}` 与正则提取 JSON，依赖 LLM 自觉遵守格式，脆弱；ChatOllama 走 Ollama 原生 function calling 与 JSON Schema，稳定可靠。此前用 requests 是误读了「不装 openai」的约束（本意是可以用 langchain-ollama，不是只能用最原始 HTTP）。

## 5. 工具设计：注入提示词 vs 工具读取

- **问题**：把报告内容注入提示词，会不会导致每次调用上下文变长？
- **结论**：采用「工具读取 + 摘要粒度 + 上下文压缩」，不用注入全文。
- **理由**：上下文长短由「喂给 LLM 的是摘要还是原文」决定，不由「注入 vs 工具」决定。agent 消费的是报告摘要（几百字），不是原始数据（几万 token）；工具读取保留 ReAct 按需获取的灵活性。工具用闭包工厂返回报告摘要，不直接持有 LangGraph State。

## 6. ReAct 解耦与中间状态

- **问题**：当前多空研究员看起来是「节点设计」而非「ReAct 架构」，loop 在哪？是否要记录中间状态（thought_history 等）？
- **结论**：loop 封装在 `react_loop` 引擎里（for + tool_calls + continue），节点层只调用它；**决定不记录中间状态**。
- **理由**：这是「机制与业务分离」的解耦——循环作为通用引擎被多头/空头/研究经理/代码生成器复用，节点层因此干净。解耦到「可复用、可替换、可单独测试」的程度，但刻意不解耦到框架黑盒，以保留轮次上限、退出原因、上下文压缩的可控性。不记录 thought_history 换取结构优化，利大于弊。

## 7. 持久化：SQLAlchemy vs PGEngine，SQL 脚本 vs create_all

- **问题**：SQLAlchemy 和 PGEngine 的区别？建表用 ORM create_all 还是 SQL 脚本？
- **结论**：用 SQLAlchemy 2.0 ORM 做 CRUD，用 SQL 脚本（`schema.sql`）建表与索引；PGEngine 不用于本项目。
- **理由**：SQLAlchemy 是通用 ORM；PGEngine 是 LangChain 针对 pgvector 向量存储的封装，本项目关系型业务表用不到。SQL 脚本能精确建索引（create_all 不自动建索引），ORM 负责运行时 CRUD，二者结构保持一致。

## 8. 舆情数据源：alphaAI vs akshare

- **问题**：舆情数据从 alphaAI 获取，但 A 股无数据。
- **结论**：改用 akshare（东方财富个股新闻）作为 A 股舆情源。
- **理由**：alphaAI 完全不支持 A 股（各 ticker 格式均 404）；Tushare news 接口无权限（需 2000 积分）；akshare 免费开源覆盖 A 股。代价是 akshare 新闻无现成情感标签，改用关键词词典做基础情感分析，后续可替换为 LLM 情感分析。

## 9. 命名术语统一

- **问题**：文档/代码中同一概念多种叫法。
- **结论**：统一为——空头研究员（废弃「分头」）、汇总节点（废弃「汇聚节点」）、策略执行 agent（废弃「策略执行器/引擎」）、研究经理（废弃「研究经历」）。
- **理由**：术语不一致会污染代码命名与沟通，已在 [术语表](../术语表.md) 记录，并同步修正所有文档与文件名。

- **结论**：建立 [模块技术文档集/技术选型总览](../模块技术文档集/技术选型总览.md)，按模块列出选型、备选、理由、权衡。

## 附：核心设计原则沉淀

1. **机制与业务分离**：可复用的循环/编排机制抽成引擎层，业务节点只声明意图。
2. **摘要优先**：agent 消费压缩后的报告摘要，不消费原始数据，控制上下文。
3. **可独立测试**：每个模块暴露清晰输入/输出，脱离完整流程可单独验证。
4. **解耦但不失控**：复用框架能力（ChatOllama/LangGraph），但保留关键可控点（轮次上限、退出原因、上下文压缩）。
