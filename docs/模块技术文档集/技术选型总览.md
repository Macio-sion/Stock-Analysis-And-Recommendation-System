# 模块技术选型总览

本文档整理系统各模块的技术选型，作为开发前的技术基线。每个模块说明选型、备选方案与选型理由，关键决策可追溯到 [架构决策记录](../架构决策记录.md)。

## 选型原则

1. **同栈优先**：优先使用 Python 生态，降低语言切换成本。
2. **成熟度**：优先选社区成熟、文档完善的方案。
3. **最小必要**：不过度设计，每个模块只引入当前阶段所需能力。
4. **可替换**：模块间通过接口解耦，便于后续替换实现。

## 各模块技术选型详解

### 1. 配置管理
- **选型**：pydantic-settings + python-dotenv
- **备选**：纯 os.environ、Dynaconf、configparser
- **理由**：pydantic-settings 提供类型校验与 `.env` 加载，与项目已用的 pydantic 同源，代码简洁。
- **权衡**：比 configparser 重，但换来类型安全与校验。

### 2. 日志
- **选型**：loguru
- **备选**：标准库 logging、structlog
- **理由**：开箱即用，支持滚动/保留/彩色输出，代码极简。
- **权衡**：与标准 logging 生态集成略弱，但本项目场景足够。

### 3. 持久化
- **选型**：PostgreSQL 16 + SQLAlchemy 2.0 + psycopg2-binary
- **备选**：SQLModel、原生 psycopg2 直写 SQL、Peewee
- **理由**：PostgreSQL 支持 JSONB（存 Agent 状态快照）与关系查询；SQLAlchemy 2.0 是 Python 事实标准 ORM，类型标注友好。
- **权衡**：SQL 脚本（`schema.sql`）负责建表与索引，ORM 负责 CRUD，二者需保持结构一致。

### 4. 缓存
- **选型**：Redis + redis-py（强制 RESP2 协议）
- **备选**：memcached、本地内存缓存
- **理由**：Redis 支持 TTL、高性能，redis-py 为官方客户端。
- **权衡**：本机 Redis 版本较老不支持 RESP3，故显式 `protocol=2` 兼容。

### 4.1 任务队列
- **选型**：Redis List/Stream + 自研 Worker
- **备选**：Celery + RabbitMQ、RQ、Dramatiq
- **理由**：Redis 已在栈内，List/Stream 足以支撑 FIFO 队列与阻塞消费；自研 Worker 轻量可控。
- **权衡**：自研需自行处理重试/超时/心跳，不如 Celery 功能全，但避免引入重型依赖。

### 5. 行情/财务数据
- **选型**：Tushare Pro（tushare 库）
- **备选**：akshare、baostock、东方财富 API
- **理由**：数据覆盖 K 线、财务指标、估值，接口稳定，token 鉴权简单。
- **权衡**：部分接口需积分/权限。

### 6. 舆情数据
- **选型**：akshare（东方财富个股新闻）
- **备选**：alphaAI（仅覆盖美股）、Tushare news 接口（需高积分）
- **理由**：akshare 免费开源，覆盖 A 股个股新闻，无需额外鉴权。
- **权衡**：依赖爬虫稳定性，新闻无现成情感标签，需自行做情感分析。

### 7. LLM 客户端
- **选型**：langchain-ollama 的 ChatOllama
- **备选**：原生 requests 调 Ollama、OpenAI SDK
- **理由**：ChatOllama 原生支持 bind_tools（工具绑定）与 with_structured_output（结构化输出），与 LangGraph 无缝集成；底层仍调用本机 Ollama。
- **权衡**：引入 langchain-ollama 依赖，抽象层略增。

### 8. ReAct 引擎
- **选型**：自研 react_engine（基于 ChatOllama 的 bind_tools）
- **备选**：LangChain AgentExecutor、原生手写循环
- **理由**：ReAct 逻辑需精细控制（轮次上限、退出原因、上下文压缩），自研更可控；工具调用走 ChatOllama bind_tools 原生协议。
- **权衡**：自研需自行处理循环控制与工具结果回填。

### 9. 工作流编排
- **选型**：LangGraph
- **备选**：手写编排、Airflow、Prefect
- **理由**：原生支持有向图、条件分支、状态共享与 checkpoint（断点续传），契合三阶段工作流。
- **权衡**：引入框架依赖，需遵循其 State/Node 范式（见 ADR-001）。

### 10. 结构化输出
- **选型**：ChatOllama with_structured_output + Pydantic v2
- **备选**：自研 output_parser 正则提取、JSON schema 手写校验
- **理由**：with_structured_output 用 JSON Schema 约束 LLM 直接返回 Pydantic 模型，稳定可靠；Pydantic v2 提供强类型校验。
- **权衡**：依赖模型对 function calling / JSON mode 的支持（qwen 支持）。

### 11. 前端
- **选型**：Streamlit
- **备选**：React/Vue + FastAPI、Gradio
- **理由**：Python 原生、开发快、内置图表，与后端同栈。
- **权衡**：交互与 WebSocket 实时能力需额外集成（见 ADR-003）。

### 12. 代码生成
- **选型**：LLM + 代码模板 + Python `ast` 静态校验
- **备选**：可视化表单生成、纯模板拼接
- **理由**：LLM 擅长自然语言转代码，AST 校验拦截危险调用，模板约束入口函数签名。
- **权衡**：生成代码不确定，需 AST 校验 + 沙箱双层兜底（见 ADR-005）。

### 13. 沙箱执行
- **选型**：Docker 容器（docker SDK）
- **备选**：受限 AST 白名单、独立子进程、远端 Serverless
- **理由**：容器提供进程/网络/文件系统隔离，配合资源限制实现强隔离。
- **权衡**：引入 Docker 依赖与容器冷启动开销（见 ADR-004）。

### 14. 实时推送
- **选型**：WebSocket
- **备选**：SSE（Server-Sent Events）、轮询
- **理由**：双向通信，支持后续交互控制（如中途停止执行）。
- **权衡**：较 SSE 实现略复杂，但满足未来交互需求。
